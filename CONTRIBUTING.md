# Робочий процес GitHub Flow

Основна гілка `main` — базова версія для спільної роботи. Кожна нова задача виконується в окремій короткоживучій гілці `feature/<id>-<name>`; виправлення — `fix/<id>-<name>`, документація — `docs/<id>-<name>`. Гілок feature може бути багато. `develop` для цього невеликого проєкту не потрібна.

## Приєднання і запуск

Репозиторій публічний на період практики: клонування доступне без авторизації. Для push власник надає учаснику доступ на запис; сторонній учасник може використати fork і PR. Учасник входить у GitHub своїм обліковим записом; паролі та токени не передаються разом із кодом.

```sh
git clone https://github.com/s6a6t6anfil-create/servicetrack-tesla.git
cd servicetrack-tesla
git config pull.ff only
git config fetch.prune true
# Вкажіть власне ім’я та адресу автора лише в цьому репозиторії:
git config user.name "Ваше ім’я"
git config user.email "Ваша підтверджена адреса GitHub або noreply"
```

Далі виконайте інструкцію встановлення в README.md. Кожен учасник створює власне віртуальне середовище, базу та локальний пароль.

## Початок задачі

Спочатку перевірте `git status`. Незавершені зміни збережіть окремим комітом у своїй гілці; не використовуйте скидання з видаленням змін.

```sh
git switch main
git pull --ff-only origin main
git switch -c feature/S01-access-checks
# Змінити код і запустити перевірки з README.md.
git diff --check
git diff
# Додавайте тільки потрібні файли:
git add path/to/changed-file
git commit -m "fix: enforce access rules for assigned mechanic"
git push -u origin feature/S01-access-checks
```

Команди з `path/to/changed-file` і назвою задачі — приклади, їх потрібно замінити фактичними шляхами та ID.

## Оновлення активної гілки й конфлікти

```sh
git fetch origin
git merge origin/main
```

Якщо є конфлікт: переглянути `git status`, вручну узгодити обидві зміни, прибрати маркери конфлікту, виконати тести, додати виправлені файли й завершити merge-коміт. Для відмови від незавершеного злиття є `git merge --abort`. Не переписувати історію спільної гілки та не використовувати force push.

## Pull request і злиття

1. Відкрити PR своєї гілки в `main`, використати шаблон: проблема, зміни, пов’язана задача, докази перевірки.
2. Дочекатися успішного CI, переглянути diff, перевірити відсутність секретів та непотрібних файлів.
3. Для командної роботи інший учасник виконує review. За індивідуального виконання самоперевірка позначається саме так і не зараховується за незалежне review з ПЗ18.
4. Після усунення зауважень власник зливає PR через squash merge; локально оновлює `main` через `pull --ff-only`.
5. Робочу гілку видаляти тільки після перевірки злиття й відсутності потрібної незбереженої роботи.

Це правила процесу. Вони не означають, що серверний захист гілки чи обов’язкове незалежне схвалення технічно ввімкнені. Для першого перенесення локальної історії застосовано одноразове наповнення `main`; наступні зміни йдуть через PR.

## Що не комітити

`.env`, `.local-secret`, `.demo-access.txt`, реальні дані клієнтів, бази SQLite, `.venv`, резервні копії й приватні ключі. При підозрі на випадкове розкриття секрету припинити публікацію та замінити скомпрометований секрет; просте видалення з останнього коміту не прибирає його з історії.
